# 쇼핑몰 상품 추천 RAG — 나이브부터 발전시키는 학습 커리큘럼

작성일: 2026-07-24

이 문서는 "나이브 RAG의 한계를 하나씩 확인하고, 그 한계를 고치는 기법을 순서대로 익힌다"는 목표로 v0~v2에서 실제로 다룬 내용과 v3 이후 계획을 정리한 것입니다. README.md의 버전별 상세 내용을 대체하지 않고, **왜 이 순서로 가는지**에 초점을 맞춘 커리큘럼 관점의 보조 문서입니다.

---

## 1. 나이브 RAG의 한계와 대응 기법

| 나이브 RAG의 한계 | 대응 기법 | 이 프로젝트에서 |
|---|---|---|
| 질문을 그대로 임베딩만 함 (조건 분해 안 됨) | 쿼리 구조화/재작성 (Query Construction) | v1에서 해결 — LLM+정규식으로 구매처/행사/예산/수량 추출 |
| 검색 단위가 부적절함 (너무 잘게 쪼개짐 / 반복 중복 심함) | 청킹 전략, 부모-자식 검색(Small-to-big) | v2에서 시도 — 거래 Row → Profile 집계 (완전히 성공하진 않음, v3 과제로 이어짐) |
| 순수 벡터검색은 정확한 키워드·희귀 단어를 놓침 | 하이브리드 검색 (BM25 + 벡터) | 아직 없음 — v4 과제 |
| 1차 검색 결과 순서가 부정확함 | 리랭커 (cross-encoder 재채점) | 아직 없음 — v4 과제 |
| 의미상 비슷해도 실제 조건(가격/MOQ/재고)에 안 맞는 게 섞임 | 메타데이터 하드 필터 | 아직 없음 — v3 과제 |
| "그럴듯하지만 근거 없는" 답변 생성(할루시네이션) | 검색·생성 역할 분리, 후보 ID 검증 | v1에서 역할 분리 완료, ID 검증은 아직 — v3 과제 |
| 개선했는지 판단할 기준이 없음 | 정량 평가 (Hit@k 등) | 아직 없음 — v3 과제 |

## 2. 버전별 커리큘럼 로드맵

| 버전 | 핵심 | 나이브 RAG의 어떤 한계를 고치는가 | 상태 |
|---|---|---|---|
| v0 | 기본 검색·추천 파이프라인 | 베이스라인 (한계 그대로 노출) | 완료 |
| v1 | 쿼리 구조화 + 거래 Row 단위 임베딩 검색 | "질문을 그대로 임베딩만 함" 문제 | 완료 |
| v2 | 거래 Profile 단위 집계 검색 | "검색 단위가 부적절함" 문제 | 완료 |
| **v3** | 하드 필터 + 역할 재분리(현재 상품 검색이 중심, 거래 Profile은 순위 보정 신호) + Hit@k 평가셋 도입 | "조건 위반 상품이 섞임" + "측정 기준 없음" 문제 | 다음 작업 |
| v4 | 하이브리드 검색(BM25+벡터) + 리랭커 | "순수 벡터검색이 키워드 놓침" + "1차 검색 순서 부정확" 문제 | 이후 |
| v5 (선택) | 멀티스텝/에이전틱 RAG (쿼리 재작성 루프, 검색 라우팅 등) | "한 번의 검색만으론 부족한 경우" 문제 | 하고 싶은 경우에만 |

이 순서를 따르는 이유: v3에서 먼저 "정답 기준(평가셋)"과 "역할분리·필터"를 갖춰두면, v4에서 하이브리드 검색·리랭커를 추가했을 때 Hit@k로 바로 "진짜 좋아졌는지"를 비교할 수 있습니다. 평가체계 없이 검색 기법부터 고도화하면 개선 여부를 판단할 수 없습니다.

## 3. v2 → v3 주요 변경사항 (참고)

v2 노트북(`notebooks/product_recommendation_v2.ipynb`) 코드 기준:

- **Profile 그룹 기준**: v2는 상품분류까지 그룹 키에 포함해 Profile을 나눔 → v3는 상품분류를 그룹 키에서 빼고, Profile 내부에 상품분류별 거래건수/비율을 저장
- **필터 방식**: v2는 예산/MOQ 위반 시 감점(0.65, 0.35 등)만 주는 soft score → v3는 판매상태·가격·MOQ를 검색 이전 단계에서 제외하는 하드 필터로 전환
- **점수 결합 구조**: v2는 검색 신호·거래 신호·조건 점수를 하나의 가중합(`final_score`)으로 섞음(거래 신호 비중 0.54 > 질문 자체 0.18) → v3는 현재 상품 검색을 1차 후보 생성의 중심에 두고, Profile 신호는 순위만 보정하는 별도 단계로 분리
- **대표상품 산출**: v2는 원본 데이터에 먼저 등장한 순서 → v3는 거래 빈도순
- **v2에 없던 것**: 관련도 임계값, 최근 거래 가중치, 추천 후보 ID 검증, 평가셋/Hit@k — 모두 v3 신규 과제

## 4. Hit@k 평가 방식에 대한 참고

Hit@k 계산 자체는 자동입니다.

```
Hit@k = (질문 N개 중, top-k 결과 안에 "정답 상품"이 하나라도 들어있는 질문 수) / N
```

다만 "정답 상품이 뭐냐"는 **처음에 한 번, 사람이 정해둬야** 합니다. 이후 v0~v4 결과를 채점하는 과정 자체는 코드로 반복 실행되는 객관적 계산입니다.

- README.md 12장의 평가 예시(`병원 개원 답례품 500개 → 타월, 위생용품, 칫솔세트`)는 **카테고리 단위**의 느슨한 정답셋
- 상품 데이터가 100건뿐이라 **상품 ID 단위**로 더 엄격한 정답셋을 만드는 것도 가능 — v3에서 평가셋 만들 때 이 방식을 우선 검토
